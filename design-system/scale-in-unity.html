Scale in Unity

How the existing product uses Scale — and how to get the parts that don't onto it. One reference in three parts: the corrections the audit found, the contrast oracle that says which token pairs are safe, and the in-situ recipes that show which component patterns hold. Everything here is colour and tokens in the Unity codebase as it ships today.

This is one of two artefacts. This one is Unity — applying Scale to the product that exists. Its companion, the Component Rulebook, is the React transition: the normative standard the rebuilt components target. Where a correction or recipe here needs a component rule, it points into the rulebook; it doesn't restate it.

Two threads run throughout. The tenant colours are being stripped back out of the product — clients no longer set the button or accent — so the contrast failures that surface could produce are designed out, not gated (Part 3). And the one input still open is the compiled Unity CSS, needed to confirm off-spec deviations; it's flagged where it matters.

Part 1
Corrections

The conformance audit's UI-only findings, as fixes to the code that ships today — chart theme, chatbot slot, admin ramp, skin hex, colour dictionaries. Each is the same shape: what's wrong, where, the before, the after with the exact token, and a grep that confirms it landed. No behaviour, no React.

In scope — the UI-only pass

Colour and tokens in the code that ships today: chart themes, skin hex, colour dictionaries, the admin ramp. Every fix below changes how the product looks, never what it does or how a user moves through it. Ships independently of the React migration.

Out of scope — lives elsewhere

Net-new components (alert, banner, tooltip, popover, drawer), the modal replacement, toast behaviour, overlay state variants. Those are builds and replacements — the rulebook's component chapters and the React migration, not a correction to existing code.

How to read a correction. The before is what's in the code now; the after is the token-correct version, with the value or variable to swap to. Contrast numbers are white-or-text against the fill shown. The grep at the foot is the done-check — it should return zero, or the expected count, when the correction has landed. Everything here is UI; where a finding has a behavioural tail, it's called out and sent to the rulebook.

One dependency to respect before you start

§2 before §1. Collapse the three colour dictionaries (B4) before migrating the tenant skins (B5), or the palette gets migrated three times — once in the skins, once in each dictionary that still hardcodes it. The order in the nav is the order to work.

Fix-now · §0

Small, high value, no dependencies

Four corrections a single dev can clear in about a day. None depends on the skin or dictionary work, so they can ship first.

B7

UI

No echarts.registerTheme exists. Series colours come from a raw eight-colour array, duplicated across two config files, so every chart in the product is wearing ECharts' out-of-the-box palette. The Scale AI Data Palette — 32 colours across five tiers — already exists and nothing consumes it.

Where: the two chart-config files (the duplicated arrays) · the palette lives in the Scale AI Data Palette

Tenant skins · §1

The long pole

The largest body of work and the one that gates client delivery — nothing reaches a tenant until it lands. One owner, sustained. The two contrast defects (A1, A2) close as part of this, not separately.

B5

Skins hardcode colour instead of seeding tokens

UI

Across 19 skins there are 62,235 raw hex literals against 67 token references. Each skin restates the entire palette in hex rather than seeding the token layer, so a change to the system has to be made 19 times. The fix inverts it: a skin sets the handful of client-overridable tokens, and everything else derives.

Part 2
Contrast — the token oracle

Every text and border token computed against every surface: the WCAG ratio and pass/fail for each pair. This proves which token pairings are safe in isolation, which to ban, and where the system has no compliant token at all.

How to read

Cells are the computed contrast ratio of that row's colour against that column's surface. Text is judged at 4.5:1 (WCAG AA, normal text); borders, icons, and focus rings at 3.0:1 (AA non-text, 1.4.11).

Result

Verdict — what the matrix bans and requires

Six rules fall straight out of the numbers. Three are bans on pairings that fail; three are gaps the token system has to fill.

FINDING 01 · BAN

Secondary text has a hard floor: neutral-11

Ban neutral-9 and neutral-10 as text of any size. They fail AA on every surface (3.85 → 2.55). Captions, helper text, secondary labels, and placeholders — placeholder is text — must be text-muted (neutral-11) or darker.

FINDING 02 · RULE

text-muted's margin runs out on row fills

Cap zebra, hover, and selected row fills at neutral-5. Muted text is 6.04 on white but 4.62 on neutral-5. On any interactive fill darker than that, step the text up to text-default.

FINDING 03 · BAN

State step-11 is a non-text colour

Never use a state step-11 for text. On its own surface it is 4.05–4.42 — below 4.5. State emphasis text is step-12; step-11 is icons and borders only.

FINDING 04 · GAP

There is no border token that meets 1.4.11

Add a --border-strong at neutral-9 or darker for perceivable control boundaries. Every current border token is under 3:1 on white — decorative only. Inputs, checkboxes, radios, toggles, and segmented controls, whose border is the affordance, have no compliant token to use. This is a hole in the system, not a misuse of it.

FINDING 05 · RULE

A state surface never carries state on its border alone

The border always pairs with the step-11 icon and step-12 text. step-7 on step-3 is 1.58–1.63 — below 3:1 by design. Consistent with the rulebook; here it is a measured fact, not a preference.

FINDING 06 · VERIFY

The focus ring thins on dark rows

Verify accent-9 against the darkest interactive fill in the product. It is 4.61 on white but 3.53 on neutral-5. If any selected or active surface is darker than neutral-5, the ring needs a darker or doubled treatment there.

Discovery (Purple) follows the identical pattern

Discovery isn't in the rulebook's embedded token layer, so it's not plotted above — but it is a step-3/7/11/12 state family like the others, so its ratios mirror info and success: step-12 text ~10:1 (pass), step-11 icon ~4:1 (non-text only), step-7 border ~1.6 (fails 3:1, decorative). Findings 03 and 05 apply to it unchanged.

SURFACE 1

The recipe passes; the failures are deviations from it

Every text role clears 4.5 when the prescribed token is used — secondary text at text-muted holds 5.4–5.9 even on the selected row. The one weak spot is the row divider (border-default, 1.41) — decorative-grade, fine unless a divider is the only thing separating rows.

Catching them in the product is a needs live input: grep the compiled CSS for secondary text bound to neutral-9/10 and row fills darker than neutral-5.

A solid status badge with white text fails AA on every state. White on error-9 is 3.87, warning-9 2.04, success-9 3.15, info-9 3.26 — the same on-fill failure as the tenant skins' warning and success. Only accent-9 carries white (4.61), because accent isn't a state colour.

SURFACE 5

A data label cannot be one colour, and one series takes no label at all

Of 34 series colours, 23 need a dark label and 11 need white — a fixed on-fill label colour fails on roughly half the palette, so the label colour must be chosen per series from its own contrast. One colour, #e54d2e, clears neither white (3.9) nor dark (4.2) at 4.5 — there is no compliant on-fill label for it; move the value off the bar or give the label its own background.

Axis, legend, and gridline text is neutral-on-white, so the neutral text floors from the matrix apply directly — text-muted minimum, never text-subtle.

SURFACE 6 · SYSTEMIC

The client colours broke in every realistic case — so they're being removed, not gated

Three of four scenarios failed, each differently — and HH Global's live CTA failure is this, already shipped. A grey-on-grey nav failed the nav pair at 3.03. A bright brand accent broke the button, links, and focus ring at once (2.04) — the warning-amber pattern, client-chosen. A mid-tone accent failed white-text and links (4.22) while passing as a ring, so a colour a client thought was fine because the focus state worked still failed its button. The table above is that record.

The fix chosen is removal, not a gate. Client branding is being stripped back out of the product, so the primary button and accent are always the system's — which pass — and a client colour can no longer land on a control. That deletes the failure mode instead of catching it on every entry, and needs no skin export. Brand expression moves to the logo, the login moment, and generated output, where a client colour can't take a control below AA. The one residual: if nav-fg / nav-bg stay client-set, the nav pair is the last place a client colour can still drop below AA — the one pair worth keeping a check on.
