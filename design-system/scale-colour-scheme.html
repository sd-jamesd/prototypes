Colour scheme and usage rules

Scale · Unity 8.0 · One rule set for the whole product, three exceptions

The rules do not differ by section. They differ by role. A chip is a chip whether it sits in a table, a modal, a trail or a widget, so the step it uses is the same in all four. What changes between sections is which roles are present, not what a role does.

Three exceptions exist and each is structural rather than stylistic: global chrome, annotation over user content, and charts. They are at the end, with the reason each one cannot follow the general rule.

5. Shape

One shape. Rounded rectangle at --radius-2, 6px, for every object inside a table cell. The Release Requests list already does this; the task list uses a pill for the same object.

The argument for the rectangle is that a pill reads as a static tag and this object is a select: it has a chevron and it opens a menu. Everything else interactive in the product is --radius-2, so a pill inside a table row reads as a different class of object than the date fields beside it, which it is not.

Do not load shape with meaning. It is tempting to say pill for static and rectangle for interactive, but that convention will be violated within a release by someone who does not know it, and then shape means nothing while looking like it means something. One radius, and let the chevron carry the affordance. The only exception is the avatar, which stays a circle because a person is a genuinely different class of object.

Four rules behind that table

RuleWhy
If it does not hover, it is not clickableA hover change is an affordance claim. A static chip that lightens on hover invites a click that does nothing. Badges and static chips have no hover state at all.
Hover moves the fill one step, never the textText at step 12 measures 9.82:1 on step 3, worst case across the ten identity families. Contrast is fixed once and cannot be broken by a state.
Selected is not a darker hoverOne step is a luminance ratio of roughly 1.06 to 1.13. That is correct for hover, which is transient and confirmed by the cursor, and wrong for selection, which persists and must be readable with no cursor present. Selection needs a second channel: a leading rule, a check, or a weight change.
Focus is always accent, never the familyFocus must be recognisable as the same thing on every surface in the product. A focus ring that changes colour with the component is not a focus ring, it is decoration.
This is the drawer defect. The nav drawer marks its selected item with a fill at 1.74:1 against the field and nothing else. No leading rule, no weight change. Which item is selected is carried entirely by a fill difference that is below the threshold for a persistent state. Adding the rule fixes it without needing to find a fill that contrasts against a saturated field, which is hard.
Primary button runs 9, 10, 11. Against white the accent ramp reads 4.61:1 at step 9, 5.57:1 at step 10 and 6.15:1 at step 11, so each state is darker than the last and the press feedback reads correctly. Note that step 11 here is hand-corrected in the ramp; if the accent is ever regenerated, re-apply the correction or step 10 and 11 will invert.

7. The three exceptions

Global chrome

The rail and drawer are the one place a saturated field is correct, because they hold navigation labels and nothing else. Everything on them is white at 4.5:1 or better. Active and hover states must differ from the field by 3:1, not by a tint, which is where the drawer currently fails at 1.74:1.

This is an exception because the general rule assumes content sits on the surface. Chrome has no content, only labels.

Annotation over user content

Annotations sit on assets of unknown colour, so no palette can guarantee contrast. Every annotation stroke carries its own 2px outline, white or black chosen by the luminance underneath. Hue is then pure identity, which is what annotation colour is for.

This is an exception because every other rule is a relationship between a foreground and a known background. Here the background is not known.

Charts

Series colour optimises for separation between series, not for contrast against a surface. Step 9 is correct here and correct nowhere else, because a series is a solid object with nothing on it. Two additional constraints apply that no other surface has: consecutive series must alternate in luminance so the chart survives greyscale printing, and lines below 3px need step 11 rather than step 9 to clear 1.4.11.

This is an exception because the constraint is perceptual distance rather than contrast ratio.
