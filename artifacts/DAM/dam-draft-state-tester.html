    Tokens in use

    Upload mode

    Upload is not a modal. It is the same dark shell as edit and bulk edit, at a third density: rail, panel, and the file list in the stage column. SCR-209 brought the rails into upload and bulk edit for exactly this reason. Two commit paths, one Primary.

    One shell, three modes. The contract holds the rail as "one component shown at two densities, never two rails. Density follows context, not mode-as-a-flag." Upload is a context, not a flag: same chrome, same rail set, same field-row kit, same action slot. Only the stage column differs, carrying the file list instead of a canvas. If it looks like a separate component in build, that is drift.
    Button tiers: Upload to library is Primary, it advances the workflow and creates the published record. Save as draft is Secondary. Scale's five tiers have no tier for an alternative commit, and Secondary is the closest fit without introducing a second Primary in one context. Flagged as a Scale evolution candidate, not a silent deviation.

    What lands in the library

    Copy discipline. The action names what happens and keeps its name downstream. Upload to library produces "3 assets added to the library". Save as draft produces "3 drafts saved". The card menu uses the same verb, Add to library. No infrastructure vocabulary anywhere in the flow, and no "Complete Upload", which describes a step that already happened.
    Not called Publish. The DAM has no publish concept in the rights model, the download surfaces or the lightbox. Publish imports a CMS mental model where content goes live to an audience. The asset is already in the library, it is just gated. Aprimo's verb for the same transition is "make available", which is close, but "library" is the noun already in the nav.

    Where this leaves upload mode

    Upload mode gains one control and loses its residency claim. It stays a transient surface with no list, no filters, no persistence. Nothing lives there. The moment a file commits by either path it is an asset in the library, findable through normal search and filter, editable in the normal detail panel, and subject to the normal bulk actions.
    The draft state already exists in production. Files are written to storage before the current Complete Upload action fires. This work names a state that has been silently live since launch and gives the user a way to see and manage it, rather than adding a new one.
    SCR-230 is written against the rejected model. Its scope persists "an in-progress upload batch as a draft (files + metadata + tag state + destination)", which is a batch object with its own storage and expiry. Under status-on-the-asset, four of its five open questions stop existing. Rewrite before Dylan scopes against it.
    Not in scope: abandoned-draft expiry. No competitor auto-deletes drafts and the failure mode is severe. If storage pressure becomes real, surface age in the drafts view and let a human decide.
