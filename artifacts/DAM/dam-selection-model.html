DAM library — selection model

Working spec for grid selection: how click, modifier, drag, and keyboard resolve; where select-all lives; and what a query-scoped selection is allowed to do. The sandbox below is the specification. Behaviour there is the acceptance criteria.

1 · Live model

The DAM renders in a 644px iframe inside the Unity host shell, so the bulk bar is pinned to a real viewport bottom rather than to the page. Every interaction is live. The inspector below the frame is harness, not product; it exposes the state machine, which is the part a developer needs to implement.

2 · Input resolution

Single click is preview. That is the frequent action and it stays the default gesture. Selection is always deliberate: modifier, marquee, checkbox, or keyboard. Behaviour does not change with selection state, so the same gesture gives the same outcome every time. This table is the contract.

3 · Select-all: one inline slot, two scopes, two objects

Both scopes share a single link in the bulk bar row, between the divider and Actions. Its label changes as scope widens; the two never appear at once. Neither is meaningful until a selection exists, which is why neither is in the toolbar. A selection is a client-side list of asset references. "All matching" is a query. They are not the same object and cannot be handed to the same consumers.

4 · Action menus: one list, three cardinalities

The card overflow menu and the bulk bar menu are not different scopes of the same thing. They are the same list at different cardinalities. Define the single-asset menu once; the others are derived from it by removing what does not survive. Source list is the menu in the current build.

Menu and bar are one overlay ground. The menu opens upward as part of the same dark panel, separated from the bar row by a 1px edge token, not floated above it as a light popover. The bar row itself stays one line: pill, close, divider, scope link, Actions. Scope counts are right-aligned on the item using the existing bulk-scope idiom rather than invented treatment.
Disabled and absent are different, and the difference is visible. Disabled means the action is possible in principle but unsafe or unrenderable at this scope, so it stays in the menu greyed with the reason in a tooltip. Absent means the action has no meaning at this cardinality, so it is not in the list at all. Rendering an absent action as permanently disabled fills the bulk menu with dead items that can never be enabled.
Suppress the card overflow menu while a selection is active. On every card, including cards outside the selection. Seven of the nine single-asset actions are already in the bulk bar, so nothing is lost for those; the cost is that Find Similar and Markup are one esc away rather than zero, which is the correct signal that they are single-asset operations. Membership-dependent visibility is worse than blanket suppression: it would leave the user working out which cards have a menu and which do not.
This is a live defect, not only a design decision. Today the overflow menu opens on a card that is part of a multi-selection, and acting from it applies to that one asset while three cards on screen show ticked checkboxes and selection borders. The card displays membership of a group while its menu means the opposite. Delete is in that menu.

7 · Gaps to close before build

Behaviour the gesture model does not yet specify, in order of consequence. Each needs an answer before the issues are scoped.

GapSeverityResolution
No keyboard navigation Blocker ⌘A and Esc are specified, but nothing moves focus between cards. A hover-revealed checkbox is not reachable at all without roving tabindex, arrow keys, Space to toggle, and Enter to open. This closes before build, not after.
Marquee origin unspecified High Empty grid space only. Mousedown on a card is reserved for drag-and-drop; if the marquee consumes it, drag-to-collection and drag-into-a-Unity-form-field become unbuildable.
Drag threshold, and what happens below it High 4px before a mousedown becomes a drag. Below the threshold on empty canvas it is a click, which clears. With a large selection and a replace-by-default marquee, a small twitch is the difference between nothing and losing the selection. Worth a second look at whether empty-space click should clear at all once the selection is large.
Double click undefined Medium No-op. The first click has already opened the preview, so without this the lightbox opens twice.
Permission-restricted assets Medium Marquee and ⌘A skip them silently. The count reports what was actually selected, not what was swept. Checkbox renders disabled with the reason in a tooltip.
Overflow menu scope during selection Live defect In the current build a card's overflow menu can be opened while a multi-selection is active, and acting from it silently applies to that one asset. Delete is in that menu and there is no undo. Resolved by suppression, in section 4, but the defect exists today and wants its own ticket ahead of this work.
Select-all scope High ⌘A selecting the loaded set is right, but the bulk bar scope ladder, the escalation to the full result set, and the cap are not in the gesture table. This is the part with the backend dependency, so it needs to land in the same issue tree rather than being picked up later. See section 3.

8 · Decisions, dependencies, open questions

What is settled, what needs a build decision, and what blocks on someone else.

Decided

Single click previews. Always, at any selection size.

Selection is deliberate: checkbox, modifier, marquee, or keyboard. The same gesture gives the same outcome regardless of state, so there is no mode to track and no silent deselect.

Decided

The anchor is never set by a preview click.

Only ctrl-click, shift-click, marquee end, Space, and shift-arrow move it. Otherwise a shift-click ranges from wherever the user last happened to look, which is unpredictable and has no visible marker.

Decided

Both select-all scopes live in the bulk bar, in one inline slot.

The link sits in the bar row itself, after the divider and before Actions. With a partial selection it reads Select all N loaded; once the loaded set is complete it becomes Select all N matching. One slot, one line, label changes with scope. Each state names its scope in words, so the widening is always stated rather than implied.

The ⌘A hint sits beside the link on the loaded rung only. The shortcut selects the loaded set and deliberately never escalates, so showing it beside Select all N matching would advertise a shortcut that does something else. Escalation stays click-only, which is also what keeps it deliberate.

The cap refusal is the one case that needs its own row, because it is a message rather than a control. It sits above the bar row on the same ground, separated by a 1px edge.

Nothing is added to the toolbar. A control that is only meaningful once a selection exists belongs where selections already live, which is also where the user is looking at the moment it becomes relevant. As sibling rungs the two scopes read as what they are: a widening of scope in stated steps.

Cold start costs two clicks, one hover checkbox on any card then rung 1, or ⌘A as a single keystroke hinted alongside the rung.

Decided

Checkbox hit target is 32px around a 16px visual.

Checkboxes stay hover-revealed in browse mode and become persistent in selection mode, so what is selected is legible without sweeping the cursor across the grid.

Decided

Marquee originates from empty grid space only.

Mousedown on a card is reserved for drag-and-drop. If the marquee consumes it, drag-to-collection and drag-into-a-Unity-form-field become unbuildable.

Decided

One action route at a time.

Browse mode acts through the card overflow menu. Selection mode acts through the bulk bar. The overflow menu is suppressed on every card while a selection is active, so the question of which route is in play and what it applies to never arises.

The two menus are one list at different cardinalities, not two lists. Define the single-asset menu once and derive the rest, so they cannot drift.

Decided

Right click is not overridden.

It would only reproduce a menu already visible on screen, and overriding it on an image grid removes browser behaviour people use on assets: open image in new tab, copy image, save image as. That is a net loss rather than a neutral swap.

Decided

The bulk bar pins to the iframe viewport, not the document.

It renders outside the scrolling grid container, absolutely positioned against the DAM's own frame, so it holds at the bottom of the 644px viewport while the grid scrolls behind it. Sticky positioning inside the scroll container looks correct on a tall page and fails in the frame: with a short result set it settles at the end of the content rather than at the bottom of the viewport.

The grid gets bottom padding equal to the bar's height so the last row is never occluded.

Dependency

Pointer capture, not document listeners.

The DAM runs as a cross-origin iframe inside Unity. A marquee wired to document.addEventListener('mousemove') freezes the moment the drag crosses the iframe boundary. Use pointer events with setPointerCapture on the grid element. This will not reproduce in a standalone HTML test.

Dependency

Query-scoped selection needs a resolve endpoint and a count.

The escalation row needs a total for the current filter, and the cap needs a server-side resolve that returns a bounded id set or refuses. This is backend work before it is frontend work, so it sequences behind the gesture model and range select.

Open

Is Markup really single-asset only?

Find Similar Assets takes one asset by definition, so its absence from the bulk menu is settled. Markup is less clear: annotating one asset within a set of three under review is a plausible workflow, and it is the sort of thing that gets requested back after launch. Treated as single-only for now. Worth a decision rather than an assumption.

Open

Does a bulk action bar exist in the build today?

It does not appear in any of the current screenshots. If it does not exist yet, the overflow menu is currently the only action route, and suppression cannot ship before the bar does. That changes the sequencing of the whole tree, so it needs confirming before the issues are scoped.

Open

Is 500 the right cap?

Chosen to keep bulk edit and the download queue tractable. Note that the live result set in the sandbox is 527, so the cap refuses on the default view and only succeeds once the user searches. That is either the cap doing its job or the cap set too low, and the screenshots are from a test library rather than a production one. Validate against the largest realistic bulk-tag or bulk-collection operation before committing to the number.

Open

Does the toolbar ever need a selection affordance at all?

With both scopes in the bulk bar, the toolbar stays exactly as shipped and this strand costs zero toolbar real estate. The open risk is discoverability of the first selection: the hover checkbox on a card is now the only visible entry point, and it is invisible until hover. Worth watching in the first demo. A persistent-on-touch variant is the likely answer if it fails, not a toolbar control.

Open

Right-click context menu: in or out of v1?

It is the accelerator that gives the desktop-native feel without touching the click model, and its contents are already specified because it mirrors the card overflow menu. Cheap, but not load-bearing. It can follow.
